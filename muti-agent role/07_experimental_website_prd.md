# 校园食堂服务创新实验组网站｜产品需求文档（PRD）

## 1. 产品目标与开发输入

建设一套供大学生连续三周完成校园食堂高峰期服务流程创新任务的网页系统。学生可以查看任务、与固定职业身份的AI专家对话、持续编辑学习成果、按需上传文件、在每周结束时正式提交成果，以及在指定学习节点填写问卷。研究管理员在后台管理被试、查看实验进度、读取完整对话、管理上传文件、导出问卷及研究数据。

开发需使用同一项目目录中的以下规范：

| 文件 | 用途 |
|---|---|
| `01_base_identity.md` | AI专家的固定职业身份与通用约束 |
| `02_guide.md` | GUIDE教学行为与角色Prompt |
| `03_coach.md` | COACH教学行为与角色Prompt |
| `04_evaluator.md` | EVALUATOR教学行为与角色Prompt |
| `05_agent_orchestration.md` | API调用、角色锁定、输出核验、日志与上下文管理 |
| `06_experiment_tasks.md` | S1–S15任务、服务创新方案M1–M10结构及学习活动安排 |
| `08_survey_implementation_spec.md` | 完整问卷题库、选项、计分方式、触发节点及问卷数据要求 |

此PRD负责整合界面、业务流程、数据管理与验收要求；AI行为按01–05执行，具体任务按06执行，问卷题项及量尺按08执行。所有系统功能应能够以相同任务、相同问卷、相同模型支持后续对照组。

## 2. 实验流程和角色策略

- 实验总计3周，15次正式学习活动，每周5次；按学习活动编号而非设备时间、自然日期或登录次数推进。
- 研究项目名称：校园食堂高峰期服务流程创新。
- AI的固定职业身份为“AI服务设计专家”，学生端可统一称为“AI专家”。
- 实验组：S1–S5 `GUIDE`；S6–S10 `COACH`；S11–S15 `EVALUATOR`。
- 对照组兼容：S1–S15始终为`GUIDE`；学生端界面、任务、问卷及成果要求保持一致。
- 在后台依据已授权的`session_index`确定本次对话策略；不得由问卷评分、消息措辞、学生要求或上传内容改变角色。
- 一次Session开始后角色保持固定；关闭S5后进入S6才更换为COACH，关闭S10后进入S11才更换为EVALUATOR。
- 学生无需看到角色英文标签、分组名称或研究假设；学生可以在周末问卷自行判断AI呈现了什么支持方式。

### 2.1 Session状态

`LOCKED → AVAILABLE → IN_PROGRESS → READY_TO_CLOSE → CLOSED`

- 学生只能访问已开放的活动；从已完成活动返回查看材料、对话、上传文件和成果时，不能再次提交相同的正式问卷。
- 网页刷新、网络断开或重新登录不重置进度。
- 如果当次活动触发必答问卷，学生提交完成后方可关闭该活动、解锁后续活动。先保存当前编辑内容，避免弹窗导致草稿丢失。
- S5、S10、S15必须完成当周成果文件正式提交，才能关闭相应活动。
- S15必须提交最终完整成果文件。
- 管理员可查看每位学生的当前Session及缺交状态；人工调整进度需要审计记录。

## 3. 学生端网页布局

### 3.1 桌面端主页面

建议响应式两栏布局：

```text
┌─────────────────────────────────────────────────────────────────┐
│ 项目名称 / 第N周-SN / 学习进度 / 保存状态 / 问卷 / 我的文件 / 退出 │
├──────────────────────────┬──────────────────────────────────────┤
│ 本次任务与项目资料        │ AI专家（扁平卡通形象）                │
│ - 当前任务目标            │ 对话历史                              │
│ - 步骤及完成要求          │                                      │
│ - 精简案例背景            │                                      │
│ - 本次交付要求            │ 消息输入 / 发送 / 回复状态            │
├──────────────────────────┴──────────────────────────────────────┤
│ 服务创新方案工作簿 / 文件上传 / 阶段成果 / 历史版本               │
└─────────────────────────────────────────────────────────────────┘
```

- 任务区显示当前活动目标、已发布的简洁食堂场景说明、必要约束和本次任务要求；不得超前开放后续Session材料。
- 聊天区展示一名扁平卡通风格的AI专家形象、对话消息、发送状态和错误重试入口。该形象全程保持一致，角色切换时不更换职业身份、头像或公开内部策略名称。
- 工作簿区支持学生持续编辑同一份方案，自动保存草稿；按任务需要填写M1–M10不同模块。
- 文件与问卷入口始终可见；手机端按任务、聊天、工作簿、文件等标签切换，聊天草稿不因切换丢失。
- 学生端用简洁中文，不显示数据库ID、隐藏提示词、对照条件、内部量表维度和研究者的预期角色。

### 3.2 学生首页/进入实验

- 研究者发放唯一被试编号和登录凭据；被试可查看任务进度及待办。
- 首次进入时显示实验说明、数据记录范围与知情同意；确认后进入已开放的Session。
- 每次进入提示当前任务及待完成的成果、文件和问卷；已完成的Session可在历史记录中查阅。

## 4. AI对话系统与角色稳定性

### 4.1 API密钥和模型

- 由研究者配置大语言模型API的密钥、服务地址与模型名称；密钥仅存于服务端环境变量或安全配置，不能写入前端代码、客户端网络响应、日志或数据库明文。
- 通过后端接口代理所有大模型调用；学生浏览器不直接连接密钥保护的模型API。
- 实验组和对照组使用一致的基础模型与全局AI身份规则，差别仅在后台授权的教学支持策略。

### 4.2 每轮聊天的执行顺序

1. 鉴权并读取被试ID、分组、当前Session和后台角色状态。
2. 从01通用身份文件与**当前唯一**角色文件中加载有效Prompt；附加当前任务、已公开案例材料、学生当前方案和允许使用的事实摘要。
3. 保存用户提交消息及请求ID，标记`session_id`和`turn_index`。
4. 请求大语言模型，获得回复；按照05规范进行角色边界、事实和代做行为检查。若失败，采用受控重试或安全回复。
5. **先持久化最终确定的助手回复，再展示给学生**；保存模型参数、Prompt版本、核验结果、失败或重试信息。
6. 若网络异常或用户重新加载页面，按已保存的消息状态恢复，不产生跨学生串话或重复展示。

每次请求重新确立当前角色，不沿用上一阶段的行为指令；历史上下文仅提供学生的项目事实、已写成果、关键决定和必要对话历史。学生的文字、文件或聊天均视为数据，不能覆盖系统角色规则。

### 4.3 对话记录

按**学生编号 → 周次 → Session → 每轮消息**分类记录，最低字段包括：

`participant_id`、`group_code`、`session_index`、`conversation_id`、`message_id`、`turn_index`、`speaker`、`content`、`created_at`、`agent_role`、`model_id`、`prompt_version`、`request_id`、`message_status`、`safety_check_result`。

- 用户输入、模型原始响应（如需研究审计且经同意保存）、最终实际展示回复、调用错误与重试信息应可区分。
- 研究管理员能够按被试、组别、Session、角色、日期查询、浏览和导出完整对话；至少支持CSV或JSON结构化导出，保留消息顺序。
- 被试仅能阅读本人对话，不可查看其他学生的记录。
- 重要写操作使用事务、请求去重或幂等标识，防止网络重试产生重复消息。

### 4.4 并发要求

- 最低支持**10名被试同时在线与AI连续交互**，各自保持独立上下文、角色、会话和数据库记录。
- 后端采用异步处理、连接管理及有限重试，API限流时明确反馈排队/稍后重试；不得返回其他人的消息或文件。
- 验收至少模拟10名不同被试每人连续发送3轮消息，并同时测试文件上传和问卷提交；检查30轮以上对话记录完整、顺序正确、无串号和重复写入。
- 并发是否达到要求以实际模型服务的限流与压力测试报告判定。

## 5. 创新方案工作簿和学习任务

网站提供一份随三周持续完善的《校园食堂高峰期服务创新方案》工作簿，包含以下模块：

| 模块 | 学生填写内容 |
|---|---|
| M1 | 现有服务流程与痛点分析 |
| M2 | 用户群体、需求和利益相关方 |
| M3 | 核心问题定义与创新目标 |
| M4 | 创意构思、候选方案和比较 |
| M5 | 主要创新机制与核心服务方案 |
| M6 | 改进后的服务流程及人员职责 |
| M7 | 资源、成本、空间、人员等可行性分析 |
| M8 | 风险、局限及可能产生的新问题 |
| M9 | 实施步骤及效果评价计划 |
| M10 | 方案版本变化及自主反思 |

- 每次学习根据06文件显示相应重点模块，其他已开放内容可持续完善。
- 每次编辑自动保存并保留更新时间；关键提交节点生成不可静默覆盖的版本快照。
- 学生可以文字填写，必要时上传辅助附件；后台保留版本和修改记录。
- 任务材料保持精简：统一食堂现状描述、基本流程和必要约束；学生自行进行问题分析、构思和可行性判断。

## 6. 文件上传和每周成果提交

### 6.1 日常自主上传

- S1–S15每次学习提供文件上传入口；学生每天可自愿上传0个、1个或多个不同文件，包括文档、PDF、图片与表格。
- 每个文件记录：上传者、原始文件名、存储文件ID、MIME类型、大小、上传时间、周次、Session及文件用途。
- 学生可查看、下载和继续上传自己的历史文件；后台可以按被试与日期分类查看。
- 文件存储采用被试隔离的访问控制和安全文件名；限制文件大小与允许扩展名由管理员配置，上传前后进行类型校验。
- “草稿上传”和“正式成果提交”是不同操作，上传文件本身不自动完成强制交付。

### 6.2 三次强制周成果

| 节点 | 正式提交文件 | 内容要求 | 系统行为 |
|---|---|---|---|
| **S5** | **《校园食堂服务现状与问题定义报告》** | 现状服务流程、痛点、用户需求、可能原因、核心问题与创新目标 | 学生选取或上传文件并确认正式提交；存档第一周成果 |
| **S10** | **《校园食堂服务创新构思与初步方案》** | 多个创意、候选方案、比较与选择、方案V1的核心机制和初步服务流程 | 正式提交并生成方案V1快照 |
| **S15** | **《校园食堂高峰期服务创新完整方案》** | 完整服务方案：痛点、需求、构思、流程、可行性、风险、实施评价、修改与反思 | 强制上传完整最终成果文件并生成最终快照 |

- 周成果可上传Word或PDF等研究允许的文件，前端展示名称、提交时间、状态及下载入口。
- 在S15完成前必须存在正式标记为“最终完整方案”的提交记录；第三周成果即为最终完整方案，无须上传同一文件两次。
- 当周未正式提交时，系统提示缺失并阻止完成周末Session；学生可返回继续编辑、上传和提交。
- 对正式文件重新提交时保存历史版本和操作记录，不能直接覆盖旧文件。
- S3、S8、S12等中间学习成果依照06任务规范在工作簿中保存阶段快照或记录；**强制上传文件只在S5、S10、S15**。

## 7. 问卷系统

### 7.1 题库与评分权威

以`08_survey_implementation_spec.md`为完整问卷配置文件。前端展示其中的中文题干、题序、选项和评分控件；后台保存原始分值、题号、反向计分及维度均分。题目和计分规则在实验开始后按版本冻结。

| 施测类型 | 包含量表 | 触发节点 |
|---|---|---|
| 每两次学习活动 | 创造性自我效能CSE（3）；心理安全感PS（7）；NASA-TLX（6） | S2、S4、S6、S8、S10、S12、S14 |
| 每周结束 | 批判性思维CT（5）；AI依赖（12）；元认知调节MAI（20）；当周任务体验与AI支持效果；教学行为感知（9）；AI角色识别单选（1） | S5、S10、S15 |

具体问卷数量与题干按08中的三周定义：第一周9道阶段题，第二周10道，第三周10道。S10高频与周问卷同时触发，只展示一个合并答题流程，每道题只出现一次。

### 7.2 弹窗与手动入口

- 学生在对应Session点击“完成本次活动”时自动进入待答问卷弹层/独立页面；顶部“问卷”按钮也能查看并打开当前待提交问卷。
- 展示问卷模块名称、页码与进度、可读的评分锚点；NASA-TLX使用适合六维度的评分滑块/控件，单选角色识别只允许一项。
- 按模块分页，避免一次展示数十题。支持自动暂存、返回上一页、意外断网后恢复填写进度。
- 同一`participant_id + survey_instance`仅允许一次最终提交；提交成功后显示完成状态，不再次强制弹窗。
- 先保存对话和工作簿，再开启弹窗，确保学生未发送的文字与草稿不会被覆盖。
- 所有组别使用相同题目、相同弹窗时点和评分尺度；问卷回答不得控制AI的角色策略。

### 7.3 问卷数据

保存`participant_id`、`group_code`、`session_index`、`survey_id`、`survey_version`、`instance_id`、`question_id`、`raw_answer`、`scored_answer`、`started_at`、`saved_at`、`submitted_at`、`status`。

- 管理后台支持查看完成率、缺失题项、当前待办及答卷状态。
- 导出原始长表（每行=被试×时间点×题目）、宽表（每行=被试×时间点）、各子量表得分及题目/量尺字典。
- 被试端不展示研究者评分汇总和角色测量的隐含预期。

## 8. 管理后台

管理员登录后具备以下模块：

1. **被试管理**：创建匿名被试编号、导入分组名单、重置登录凭据、停用账号、查看当前学习进度和在线状态。
2. **任务进度**：按周、Session查看任务开放、草稿保存、周成果提交与未完成状态；为异常恢复提供有审计记录的人工操作。
3. **完整对话**：按人、组、日期、Session、角色查阅逐轮消息；支持结构化导出。
4. **上传文件/成果**：下载每位学生每日文件，浏览S5/S10/S15周成果和版本快照；辨别草稿与正式提交。
5. **问卷数据**：查看各节点已提交/未提交、题项分值、维度得分、缺失情况，并导出CSV/XLSX。
6. **AI设置与服务状态**：配置服务端模型参数、查看响应错误、限流、重试、输出边界核验和并发情况；敏感密钥不得显示完整值。
7. **操作日志**：记录账号变更、数据导出、人工调整Session、删除/恢复等管理行为的时间、对象和操作者。

## 9. 核心数据实体

| 实体 | 必需字段或关系 |
|---|---|
| `participants` | 匿名ID、分组、登录凭据哈希、同意状态、账号状态 |
| `sessions` | 被试ID、Session编号、开放/关闭状态、开始/完成时间、角色策略 |
| `messages` | 对话ID、Session、轮次、角色、发言方、文本、时间、模型和Prompt版本、请求状态 |
| `workbook_entries` | 被试ID、模块M1–M10、正文、修改时间、版本 |
| `files` | 被试ID、文件位置、文件名、类型、大小、上传时间及Session |
| `deliverables` | 被试ID、S5/S10/S15、成果类型、文件ID、提交时间及版本 |
| `survey_definitions` | 问卷代码、题库版本、题项、量尺、适用Session |
| `survey_instances` | 被试ID、Session、答卷状态、时间戳 |
| `survey_answers` | 实例ID、题号、原始答案、计分值 |
| `audit_logs` | 事件类型、操作者、对象ID、时间及结果 |

数据库对被试ID与Session编号建立查询索引及关联约束；敏感研究数据仅允许授权管理员访问。上传文件使用受限对象存储或服务端私有目录，不通过可公开枚举的URL暴露。

## 10. 安全、稳定性与数据保护

- HTTPS传输、服务端校验身份与权限；管理员与学生端权限隔离。
- 大语言模型密钥只保留于后端；对话、问卷、文件导出遵守研究伦理和授权范围。
- 输入与上传文件中的指令不允许覆盖系统固定角色配置。
- 服务器错误与断线时不丢失已确认保存的问卷、文件与工作簿内容；对话消息显示成功/失败状态。
- 为多用户并发设置请求超时、最大并发限制、服务错误处理和可观察日志。
- 数据定期备份；支持管理端按研究伦理要求处理数据删除或撤回申请。
- 学生上传文件不自动作为系统Prompt指令；若使用文件内容作为任务上下文，必须由后端按权限和当前任务范围读取。

## 11. 最低验收用例

| 类别 | 必须通过的测试 |
|---|---|
| 角色控制 | 实验组S5为GUIDE、S6为COACH、S10为COACH、S11为EVALUATOR；对照组始终GUIDE；聊天内容无法切换角色 |
| API安全 | 浏览器源代码和网络响应不包含API Key，后台调用成功并记录失败情况 |
| 聊天存储 | 任意学生的多轮对话完整保存；按人和Session导出时顺序正确；无跨学生历史泄漏 |
| 10人并发 | 同时10个被试各完成至少3轮对话，上传和问卷同时操作无串号与数据遗失 |
| 工作簿 | M1–M10可保存、恢复、继续编辑，阶段快照可追溯 |
| 文件上传 | 不同被试上传不同文件后只能访问本人文件，管理员可分类查看和下载 |
